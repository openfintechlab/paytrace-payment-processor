# PayTrace Payment Processor

## Introduction

`paytrace-payment-processor` is a long-running worker that consumes payment request messages from RabbitMQ, validates them against the PayTrace payment instruction schema, converts each request to ISO 20022 `pain.001.001.03`, posts it to the ISO 20022 adapter, records row processing status in PostgreSQL, and publishes a downstream processing event.

The current processor is not a FastAPI service and does not expose HTTP routes or health endpoints. It runs from `src/main.py` and keeps a RabbitMQ listener alive in the foreground process.

## Responsibilities

- Load `OFTL_*` configuration from `.env` and process environment.
- Validate PostgreSQL connectivity at startup.
- Validate RabbitMQ connectivity at startup and bind consumers to the domestic and cross-border request queues.
- Consume JSON payment instructions generated by `paytrace-file-ingest-csv`.
- Reject invalid JSON, unknown fields, unsupported queues, and schema-invalid payment payloads.
- Map valid instructions to ISO 20022 `pain.001.001.03` XML.
- POST XML to the configured ISO 20022 adapter endpoint.
- Parse adapter `pacs.002`/payment status XML responses.
- Mark `oftl_fwcsv_row_dispatch` rows as `processed` or `failed`.
- Publish EV003 `payment.row.processed` events for both successful and failed downstream processing outcomes.

## Project Structure

```text
src/
  main.py                         # Entrypoint, startup checks, listener lifecycle
  domain/
    PaymentRequestHandler.py      # Message decoding, validation, DB status updates, EV003 publishing
    Iso20022AdapterPoster.py      # HTTP POST helper for the ISO 20022 adapter
    Iso20022MessageMapper.py      # pain.001 builder and pacs.002 parser
    payment_instruction.schema.json
  utilities/
    ConfigLoader.py               # Loads valid OFTL_* variables from .env and process env
    DBHelper.py                   # SQLAlchemy PostgreSQL helper
    Logging.py                    # Centralized logging wrapper
    RabbitMQHelper.py             # RabbitMQ consumer and publisher helper
tests/
  test_*.py                       # Focused unit tests for config, DB, RabbitMQ, handler, adapter mapping
```

## Prerequisites

- Python 3.11+
- `uv`
- PostgreSQL with the PayTrace CSV ingest tables provisioned
- RabbitMQ
- ISO 20022 adapter service reachable from this worker

## Quick Start

Create and update the local environment file:

```bash
cp .env.example .env
```

Install dependencies:

```bash
uv sync
```

Run the processor:

```bash
uv run python src/main.py
```

The process exits with code `99` when RabbitMQ connection retries are exhausted, and exits with code `91` for other startup/runtime failures.

## Docker

Build the image from this project root:

```bash
docker build -t paytrace-payment-processor:latest .
```

Run with an environment file:

```bash
docker run -d \
  --name paytrace-payment-processor \
  --env-file .env \
  paytrace-payment-processor:latest
```

When running against services on the host from Docker Desktop, set host values such as `OFTL_POSTGRESDB_HOST=host.docker.internal` and `OFTL_RABITMQ_HOST=host.docker.internal`.

## Configuration Reference

`ConfigLoader` only accepts uppercase keys matching the `OFTL_*` naming pattern. Process environment values override values in `.env`. Values whose key ends with `_SECRET` are passed through the placeholder decrypt hook.

Do not commit real credentials. Keep real values in local `.env` or a managed secret store; commit only safe templates such as `.env.example`.

### Logging

- `OFTL_LOG_LEVEL` - log level, for example `INFO` or `DEBUG`
- `OFTL_LOG_FORMAT` - Python logging format string

- `OFTL_RABITMQ_USERNAME`

- `OFTL_RABITMQ_CONNECTION_ATTEMPTS` - default `3`
- `OFTL_RABITMQ_CONN_RETRYCOUNT` - application-level connection retry count, default `3`
- `OFTL_RABITMQ_RETRY_DELAY` - default `2`
- `OFTL_RABITMQ_SOCKET_TIMEOUT` - default `5`

- `OFTL_RABITMQ_PREFETCH_COUNT` - default `1`
- `OFTL_RABITMQ_AUTOACK` - default `true`; set `false` to acknowledge only after handler success

- `OFTL_RABITMQ_DOEMSTIC_REQUEST_QUEUE` - domestic payment request queue, default `CSV.PAYMENTS.DOMESTIC.REQ`
- `OFTL_RABITMQ_CROSS_BORDER_REQUEST_QUEUE` - cross-border payment request queue, default `CSV.PAYMENTS.CROSS_BORDER.REQ`

The variable name `OFTL_RABITMQ_DOEMSTIC_REQUEST_QUEUE` intentionally matches the current code spelling.

### RabbitMQ Event Publishing

- `OFTL_RABITMQ_SAGA_EXCHANGE` - topic exchange used by this processor for EV003, default `paytrace.events`
- `OFTL_RABITMQ_PUBEVENT_EV003` - EV003 routing key, default `payment.row.processed`
- `OFTL_RABITMQ_EXCHANGE_DURABLE` - default `true`
- `OFTL_RABITMQ_MESSAGE_PERSISTENT` - default `true`
- `OFTL_RABITMQ_PUBLISH_MANDATORY` - default `false`
- `OFTL_RABITMQ_EXCHANGE_TYPE` - default `direct` when no exchange type is passed; EV003 publishing explicitly uses `topic`

### ISO 20022 Adapter

Required:

- `OFTL_HTTPURL_ISO20022ADAP` - endpoint that accepts ISO 20022 `pain.001.001.03` XML and returns a status XML response

Optional:

- `OFTL_HTTPURL_ISO20022TIMEOUT` - HTTP timeout in seconds, default `5`
- `OFTL_HTTP_AUTHORIZATION_SECRET` - outbound `Authorization` header
- `OFTL_HTTP_X_TRANSACTION_ID` - outbound `x-transaction-id`; defaults to `transfer_id`
- `OFTL_HTTP_X_CORRELATION_ID` - outbound `x-correlation-id`; defaults to the RabbitMQ message correlation ID
- `OFTL_HTTP_IDEMPOTENCY_KEY` - outbound `idempotency-key`; defaults to `transfer_id`
- `OFTL_HTTP_ACCEPT_LANGUAGE` - outbound `Accept-Language`
- `OFTL_HTTP_CONTENT_TYPE` - outbound `Content-Type`, default `application/xml`

The HTTP request always includes `Accept: application/xml`.

## Runtime Flow

1. `src/main.py` loads configuration and initializes logging.
2. `DBHelper.initialize_connection()` opens a PostgreSQL engine and runs `SELECT 1`.
3. `RabbitMQHelper.initialize_connection()` validates RabbitMQ settings and declares both request queues.
4. `RabbitMQHelper.start_listener()` starts a background consumer thread.
5. `PaymentRequestHandler.handle_message()` decodes each queue message as UTF-8 JSON.
6. The handler removes null/empty optional values, coerces numeric fields to decimals, and validates against `payment_instruction.schema.json`.
7. Domestic queue messages are sent through `Iso20022AdapterPoster.post_domestic()`.
8. Cross-border queue messages are sent through `Iso20022AdapterPoster.post_crossborder()`.
9. The adapter response is parsed. Accepted statuses are `ACTC`, `ACCP`, `ACFC`, `ACSP`, `ACSC`, `ACWC`, and `RCVD`.
10. The worker publishes EV003 and then updates `oftl_fwcsv_row_dispatch` to `processed` or `failed`.

## Source Messages and Events

The source for this processor is `paytrace-file-ingest-csv`. That worker publishes one JSON payment request per valid CSV row to one of the request queues:

- `CSV.PAYMENTS.DOMESTIC.REQ` for `transfer_type=DOMESTIC`
- `CSV.PAYMENTS.CROSS_BORDER.REQ` for `transfer_type=CROSS_BORDER`

The file-ingest source also publishes its own lifecycle events to `OFTL_RABITMQ_PUBEVENT_EXCHANGE`:

- EV003 `payment.row.processed` when a CSV row is processed and published to RabbitMQ, with `payload.processing_status=published` or `failed`. 

> Please refer to [Paytrace Business Events](https://github.com/openfintechlab/pytrace-backlogs/wiki/Business-Events) for the EV003 schema.

This payment processor does not consume EV001 or EV002. It consumes the row request messages generated by the source and publishes EV003 after downstream ISO 20022 processing.

## Inbound Payment Request Contract

Inbound RabbitMQ message bodies must be JSON objects that match `src/domain/payment_instruction.schema.json`. Unknown fields are rejected.

Required fields:

- `transfer_id`
- `transfer_type`
- `transaction_datetime`
- `requested_execution_date`
- `amount`
- `currency`
- `debtor_name`
- `debtor_country`
- `debtor_account_scheme`
- `debtor_account_id`
- `debtor_bank_id_scheme`
- `debtor_bank_id`
- `creditor_name`
- `creditor_country`
- `creditor_account_scheme`
- `creditor_account_id`
- `creditor_bank_id_scheme`
- `creditor_bank_id`

Optional fields:

- `purpose_code`
- `charge_bearer`
- `exchange_rate`
- `intermediary_bank_bic`
- `remittance_unstructured`
- `remittance_reference`

Important validation rules:

- `transfer_type`: `DOMESTIC` or `CROSS_BORDER`
- `transaction_datetime`: ISO 8601 date-time
- `requested_execution_date`: ISO 8601 date
- `amount`: numeric, minimum `0`, two-decimal multiple
- `currency`: three uppercase ISO 4217-style letters
- country fields: two uppercase ISO 3166-1-style letters
- account schemes: `IBAN`, `BBAN`, or `OTHER`
- bank id schemes: `BIC` or `LOCAL`
- `purpose_code`: `SALA`, `SUPP`, `INVC`, `TAXS`, or `RENT`
- `charge_bearer`: `DEBT`, `CRED`, or `SHAR`

## EV003 Payment Row Processed Event

The processor publishes EV003 to `OFTL_RABITMQ_SAGA_EXCHANGE` as a RabbitMQ `topic` exchange message. The routing key comes from `OFTL_RABITMQ_PUBEVENT_EV003` and defaults to `payment.row.processed`.

EV003 is published for:

- successful adapter processing, with `payload.processing_status=processed`
- adapter rejection, invalid inbound messages, unsupported queues, and adapter connectivity failures, with `payload.processing_status=failed`

Envelope:

```json
{
  "event_id": "generated UUID",
  "event_code": "EV003",
  "event_type": "payment.row.processed",
  "event_version": "1.0",
  "timestamp": "UTC ISO-8601 timestamp",
  "source": "paytrace-payment-processor",
  "correlation_id": "RabbitMQ correlation_id or generated UUID",
  "causation_id": "transfer_id when available",
  "payload": {
    "processing_status": "processed",
    "message_payload": {
      "transfer_id": "PTX-0000001"
    },
    "adapter_response": {
      "success": true,
      "status_code": "ACTC",
      "status_description": "ACTC",
      "raw_message": "adapter XML response",
      "message_id": "adapter message id when present",
      "transaction_status": "ACTC",
      "reason_code": null
    },
    "error_message": null
  }
}
```

RabbitMQ message properties include:

- `correlation_id`: resolved event correlation ID
- `message_id`: generated event ID
- `content_type`: `application/json`
- `content_encoding`: `utf-8`
- `delivery_mode`: persistent when `OFTL_RABITMQ_MESSAGE_PERSISTENT=true`

EV003 headers:

```json
{
  "event_code": "EV003",
  "transfer_id": "PTX-0000001",
  "processing_status": "processed"
}
```

## Database Side Effects

The processor writes to `oftl_fwcsv_row_dispatch` using an upsert keyed by `transfer_id`.

On success:

- `status` is set to `processed`
- `request_queue` is set to the queue that delivered the message
- `published_at` is preserved or set to `NOW()`
- `updated_at` is set to `NOW()`
- `error_message` is cleared

On failure:

- `status` is set to `failed`
- `request_queue` is set to the queue that delivered the message
- `updated_at` is set to `NOW()`
- `error_message` stores the failure detail, truncated to 2000 characters

If no previous row exists, `file_id` defaults to `payment-processor` and `row_number` defaults to `0`.
